## What Lovable manages

Rules outside this block are the project's own. Change the pieces below in
Lovable, not by hand. With the [Lovable MCP](https://mcp.lovable.dev)
connected, `send_message` asks Lovable to do it; otherwise ask the user to
use the editor.

- **Database.** Do not add or edit `supabase/migrations/` or `drizzle/`.
  Ask Lovable to change the schema.
- **Generated files.** Do not edit a file whose header says it is automatically
  generated.
- **AI gateway.** Keep model calls on Lovable's gateway, and keep
  `LOVABLE_API_KEY` out of browser code.
- **Connectors.** Lovable provides native connectors. `list_connectors` shows
  which are enabled; `add_connector` only returns the dashboard link. When a
  connector is enabled, calls go through the connector gateway and need
  `LOVABLE_API_KEY`. When Lovable does not provide one, users can bring their
  own key and store it in Secrets.
- **Secrets.** Lovable manages them. Do not put secret values in the repo.

## FlashReserve architecture
- Use TanStack Start file routes with leaf metadata and Outlet-only parents to retain the supported runtime and typed navigation.
- Separate customer and operations shells while sharing semantic tokens because the audiences need different navigation and density.
- Centralize integration state and reject unverified reads instead of guessing contracts to prevent false commerce results.
- Keep private operations fail-closed until existing production auth and roles are verified to prevent sensitive disclosures.
- Do not replace the external NestJS database or auth service because its API remains authoritative.
- Monorepo: the web app stays at the repo root (required by the Lovable preview); shared API contracts live in packages/shared-types and the NestJS service goes in apps/backend, so both sides share one source of types.
